### Detail

#### 1. [P1] Default loopback dashboard has no authentication

- **Location:** `dashboard/server.js:311`
- **What:** When no auth file or credentials are configured, every request passes authentication. The default server binds to loopback, which other local accounts on a shared host can also access; `/api/config` returns the user's personal fields.
- **Trigger:** Start the dashboard with no AIDR credentials or auth file on a shared NAS or VPS, then have another local account request `/api/config`.
- **Impact:** Another local user can read the user's identity data and access other dashboard endpoints, including those that start real runs.
- **Fix:** Require authentication for sensitive dashboard routes even on loopback, or provide a mode that explicitly restricts access to the owning user.
- **Disposition:** fixed 6b32217 (no credentials means the server refuses to start, loopback included, and every route but `/api/health` answers 401; `AIDR_DASHBOARD_NO_AUTH=1` is the documented opt-out for tests and development, on a loopback bind only and only when no login existed at start-up; `aidr dashboard` generates a login)

#### 2. [P1] Registry URLs can direct PII to an unrelated public site

- **Location:** `generic-runner.js:1341`
- **What:** Feed rows are accepted as broker URLs based on an `http` prefix, without checking that the host belongs to the named broker. The generic runner can then fill and submit an opt-out-looking form on that site.
- **Trigger:** A poisoned or compromised registry row supplies an attacker-controlled public URL with an opt-out path and form.
- **Impact:** The unattended run can submit the user's name, email, address, and other configured fields to the attacker's site.
- **Fix:** Require an operator-approved broker host or a verified domain match before automating a feed entry.
- **Disposition:** fixed e8d98ec (a registry row is automated only when its host belongs to the named broker: its own listed domain, one derived from its company name, or a domain the shipped datasets know as that broker's; everything else becomes a manual row that is never navigated to; 7 of 459 shipped Markup rows turn manual, 0 of 14 BADBOOL)

#### 3. [P1] DNS lookup errors fail open and cached verdicts can permit SSRF

- **Location:** `generic-runner.js:291`
- **What:** A failed or timed-out DNS lookup is treated as allowed. `makeUrlChecker` then caches that positive verdict by origin, while Playwright resolves the host independently, so the browser can reach a private address without the landing check detecting it.
- **Trigger:** A registry URL uses an attacker-controlled host whose DNS lookup times out or returns a public IP to Node, then resolves to a private address for the browser.
- **Impact:** The browser can send requests to internal services; if the returned page has a fillable opt-out form, the runner may also send the user's PII there.
- **Fix:** Fail closed on DNS errors and validate or pin the destination IP for the browser's actual requests and redirects.
- **Disposition:** fixed 6474287 (`lib/url-guard.js` holds one address table; a DNS error, timeout or empty answer is a refusal, every navigation request is intercepted with no cached verdict, and the address the browser actually connected to is compared)

#### 4. [P1] Any non-rejected 2xx confirmation page is recorded as success

- **Location:** `lib/imap-confirm.js:871`
- **What:** After checking only the HTTP status and a short list of rejection phrases, `clickConfirmLink` returns `ok: true` without requiring positive confirmation evidence. The caller then records success.
- **Trigger:** A confirmation link returns HTTP 200 or 204 with a login wall, generic page, or other response that contains none of the rejected phrases.
- **Impact:** The pending request is marked confirmed and skipped for 90 days even though the broker may not have completed the opt-out.
- **Fix:** Require a positive confirmation signal; treat unknown response pages as unverified and keep the request pending.
- **Disposition:** fixed df0067f (`lib/imap-confirm.js` requires a page that says it worked; failure wording and a login or bot wall are failures, and a page that says nothing is `unverified`: the request stays pending and no success is recorded)

#### 5. [P2] Editing an encrypted config writes it to plaintext first

- **Location:** `setup.js:518`
- **What:** On an already-encrypted install, setup writes the updated full config to `config.json` before re-encrypting and shredding it later. An interruption or encryption failure leaves that plaintext file behind.
- **Trigger:** Rerun setup with a readable encrypted config and the process stops or encryption fails after `saveConfig(config)`.
- **Impact:** The config, including PII and credentials, remains unencrypted on disk; an in-place encrypted config may also be overwritten before its replacement is secured.
- **Fix:** When `prior.encrypted` is true, write the updated config directly as an encrypted envelope without first calling `saveConfig`.
- **Disposition:** fixed 77edafd (`setup.js` `persistConfig` writes the envelope straight into the file the config came from, `.enc` or in place, and never writes a plaintext `config.json` first)

#### 6. [P2] Broker account passwords are echoed at the prompt

- **Location:** `setup.js:502`
- **What:** The account password is read with `ask()`, which uses the normal echoing readline prompt; the hidden-input `askSecret()` helper is not used.
- **Trigger:** In a terminal setup, choose to configure a broker account and type its password.
- **Impact:** The password is visible on screen and may be captured by terminal recording or scrollback.
- **Fix:** Read `acctPass` with `askSecret()`.
- **Disposition:** fixed 77edafd (broker account passwords go through the secret prompt, and stored secrets are no longer printed as prompt defaults)

#### 7. [P2] Confirmation links with tokens are returned unredacted

- **Location:** `lib/imap-confirm.js:1066`
- **What:** The processed result includes the raw confirmation URL even though the module already has `redactedUrl()`. The caller prints this URL, exposing query tokens in stdout and any captured dashboard or service logs.
- **Trigger:** Process a confirmation email whose link carries a token in its query string.
- **Impact:** A bearer confirmation link, and potentially an embedded user identifier, is copied into logs where it can be replayed or disclosed.
- **Fix:** Return a redacted URL in result objects and keep the raw URL only for navigation.
- **Disposition:** fixed df0067f (results, errors and dry-run entries carry the confirmation link as host and path only; the raw link is used only to navigate)

#### 8. [P2] Broker response snippets can persist the user's PII

- **Location:** `generic-runner.js:530`
- **What:** `judgeNewText()` returns raw text around confirmation wording as `detail`; the run loop logs that detail and passes it to state-recording functions. A broker page that echoes the submitted email or other identity data can therefore persist it in logs and state.
- **Trigger:** A broker's success or email-confirmation page includes the user's email or name near its confirmation text.
- **Impact:** PII is retained in run logs and `state.json`, where dashboard readers can also retrieve it.
- **Fix:** Redact configured identity values from response snippets before logging or recording them, or store a fixed status detail instead.
- **Disposition:** fixed f2d7a5d (`lib/redact-identity.js` removes the person's own details from the page snippet before `generic-runner.js` logs or records it, `judgeNewText`; the explicit-broker runner got the same in 8d5061d)
