### Detail

#### 1. [P1] Complaint files inherit permissive default permissions

- **Location:** `lib/complaint.js:308`
- **What:** The complaint directory and TXT files are created without owner-only modes; the PDF writer also receives no restricted mode. With a typical 022 umask, files are readable by other local accounts.
- **Trigger:** Run complaint generation on Linux or macOS with overdue entries and the default umask.
- **Impact:** Other local users can read the complainant’s name, location, email, and phone from the generated reports.
- **Fix:** Create the directory with mode 0700 and restrict both TXT and PDF files to 0600.
- **Disposition:** fixed 6e49729 (the complaints directory is 0700 and every TXT and PDF 0600, also tightened when it already existed; the shared owner-only writers are 7c9f5a9, `lib/complaint.js` `_writePrivate`)

#### 2. [P1] Registry URLs can direct the browser to arbitrary hosts

- **Location:** `generic-runner.js:484`
- **What:** Feed URLs are accepted if they merely start with `http`; they are later navigated to and their forms may be filled with the user's PII. Neither private addresses nor redirects are restricted.
- **Trigger:** A registry row contains an attacker-controlled, loopback, private, or link-local URL, or redirects to one.
- **Impact:** The browser can reach internal services or send PII to a malicious form during the unattended run.
- **Fix:** Validate the broker target before navigation, reject non-public addresses, and revalidate every redirect against an approved broker origin.
- **Disposition:** fixed 80ed160 (every row is refused before navigation and the landed URL re-checked: http(s) only, no credentials, no loopback, private or link-local addresses; DNS and per-navigation hardening in 6474287, and a row is automated only when its host belongs to the named broker in e8d98ec)

#### 3. [P1] Registry homepage URLs are processed as opt-out forms

- **Location:** `generic-runner.js:489`
- **What:** The feed’s `method` is ignored when rows are added. A homepage classified as `manual` is still sent to the generic form filler, which can fill and submit a newsletter or marketing form.
- **Trigger:** A registry lists a broker’s homepage rather than a dedicated opt-out page, and that page has a generic form.
- **Impact:** The tool sends the user's name and contact details to an unintended form instead of requesting removal.
- **Fix:** Only enqueue verified opt-out URLs classified as `direct-form`; keep manual or homepage entries out of automatic submission.
- **Disposition:** fixed eaf000c (only a form that reads as opt-out, deletion or privacy request is filled, never a newsletter, login or contact form; the feed row's own `method` is honoured in 8e7244d, so a manual or homepage row is never submitted)

#### 4. [P1] A successful button click is treated as an accepted opt-out

- **Location:** `generic-runner.js:410`
- **What:** After `submitForm()` returns true, the runner reports success unless it detects an email-confirmation message. It does not require positive success evidence or reject ordinary validation/server errors; a click can return true even when browser validation prevents submission.
- **Trigger:** A generic form has an unfilled required field or returns an error without email-confirmation wording.
- **Impact:** The tool records `lastSuccess` and suppresses retries while reporting the broker as opted out, although no removal request was accepted.
- **Fix:** Require explicit post-submit success evidence; report failures or unknown outcomes as errors or unverified.
- **Disposition:** fixed eaf000c (a click is judged on the NEW page text after it: success wording is success, failure wording an error, anything else `unverified`, which records no `lastSuccess` and starts no 90-day cooldown)

#### 5. [P2] SMTP acceptance is recorded as removal success

- **Location:** `lib/email.js:156`
- **What:** A successful `sendMail()` call proves the message was accepted by the mail transport, not that the broker removed the data. The code records it as `lastSuccess`, which starts the 90-day skip window.
- **Trigger:** SMTP accepts an opt-out email but the broker ignores it or does not complete the request.
- **Impact:** The dashboard can count the broker as opted out and the tool delays follow-up for 90 days without evidence of removal.
- **Fix:** Track email delivery separately from confirmed removal and avoid counting delivery as an opt-out success.
- **Disposition:** wontfix: the 90-day window is the re-send interval; the log now says the email was sent, not that data was removed (the wording change is 2a92479; SMTP acceptance still records `lastSuccess` on purpose, so an email broker is not mailed again every run)

#### 6. [P2] Preview output includes raw form values

- **Location:** `lib/broker-runner.js:168`
- **What:** Preview mode formats every populated input value into `detail` and sends it to `logResult()`, which prints it to stdout; the dashboard also streams child output.
- **Trigger:** Run `--preview` from the CLI or dashboard on a form containing the user's details.
- **Impact:** PII appears in terminal output, dashboard streams, and any service or container log collector capturing stdout.
- **Fix:** Show field names and fill status only; redact all field values in preview output.
- **Disposition:** fixed e8f6360 (preview prints field names and filled or empty only, and strips the query string from the target URL; error details and the listing line are reduced to hosts)

#### 7. [P2] Freeze updates can overwrite concurrent opt-out state

- **Location:** `dashboard/server.js:618`
- **What:** The freeze handler reads and rewrites the entire state file without the runner’s process lock. Atomic rename prevents torn files but does not prevent a stale read-modify-write from winning.
- **Trigger:** Toggle a freeze target while a watcher run is updating `state.json`.
- **Impact:** The dashboard write can erase newer opt-out history, leading to repeated submissions or lost pending state.
- **Fix:** Use the same state lock and shared save path, or store freeze status separately from opt-out state.
- **Disposition:** fixed 6f6f8c7 (`dashboard/server.js` `withStateWriteAccess` answers 409 while a run is live or another process holds the state lock, and takes the lock itself for the read-modify-write; the pure transition is `applyFreeze` from c00248e, tests in 0ef044e)

#### 8. [P2] A data-access request can trigger a deletion complaint

- **Location:** `lib/complaint.js:77`
- **What:** `resolveRequestedAt()` prioritizes `knowRequestedAt`, even though that timestamp records a disclosure request, not an erasure request. Complaint generation then describes it as a verified deletion request.
- **Trigger:** A broker has an overdue right-to-know request but no deletion request recorded.
- **Impact:** The tool can generate a regulator complaint containing the user's PII and a false claim that the broker ignored a deletion request.
- **Fix:** Do not use `knowRequestedAt` for deletion complaints; handle overdue access requests with a separate, accurate complaint type.
- **Disposition:** fixed 6e49729 (`resolveRequestedAt` dates a deletion request from `lastSuccess` only, never `knowRequestedAt`, and a complaint needs a `verifiedStillListedAt` after the deadline; overdue right-to-know requests are reported by `findOverdueKnowRequests`, never filed as a deletion complaint)

#### 9. [P2] Confirmation navigation trusts redirects after validating the initial URL

- **Location:** `lib/imap-confirm.js:364`
- **What:** The extracted URL is checked against the broker host, but `page.goto()` follows redirects without checking the final destination; the code later records success after any non-throwing navigation.
- **Trigger:** A broker-hosted confirmation link or open redirect sends the browser to an unrelated or private address.
- **Impact:** The confirmation workflow can visit an unintended destination and mark the broker successful without evidence that removal was confirmed.
- **Fix:** Restrict redirect targets and final URLs to approved broker hosts, and require explicit confirmation evidence before recording success.
- **Disposition:** fixed 8c8b62d (every navigation and redirect is route-guarded to the broker host with no private or loopback address, the final `page.url()` is validated, and the status must be below 400; a page that shows no confirmation is `unverified` and records nothing in df0067f)

#### 10. [P2] Multi-person complaint files overwrite each other

- **Location:** `lib/complaint.js:306`
- **What:** Complaint filenames include only broker and agency, so complaints for different people sharing the same broker and agency resolve to the same paths.
- **Trigger:** Two configured people have overdue entries for the same broker and regime.
- **Impact:** The later TXT/PDF overwrites the earlier person’s report, leaving one complaint missing.
- **Fix:** Include a sanitized person identifier or unique suffix in each complaint filename.
- **Disposition:** fixed 6e49729 (complaint filenames carry a person slug and are made unique within a run, `writeComplaintFiles` in `lib/complaint.js`)
